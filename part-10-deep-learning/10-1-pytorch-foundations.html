10.1 PyTorch Foundations

A torch.Tensor is a NumPy array that knows three extra things: where it lives (device: CPU/GPU), how precisely (dtype: usually float32), and how it was made (the autograd graph). Everything else — broadcasting, reshaping, @, reductions — transfers from NumPy almost word-for-word. This page builds that mental model with live NumPy cells; the PyTorch itself runs in the companion lab.

Tier 3 — PyTorch does not run in this browser. Concept cells below are live NumPy; the full PyTorch lab runs in Colab:

1. Basic Concept

NumPy PyTorch Note
np.float64 arrays torch.float32 default torch defaults to 32-bit (GPU-friendly)
X.reshape(3, -1) X.reshape(3, -1) identical
A @ B A @ B identical
X.astype(np.float64) X.to(torch.float64) dtype casting
— X.to("cuda") device movement (new concept)
— w.requires_grad / w.grad autograd (new concept)
— loss.backward() reverse-mode differentiation (new concept)

The three additions, in one breath:

  1. Autograd — every op on a tensor with requires_grad=True records a node in a computation graph; loss.backward() walks it in reverse and accumulates ∂loss/∂parameter into each .grad.
  2. Devices — the same tensor code runs on CPU or GPU; tensors on different devices cannot be mixed.
  3. torch.nn + torch.optim — layers, losses, and optimizers as composable objects (10.2 onward).

Worked example — the graph autograd automates, computed by hand (live NumPy): one gradient-descent step of linear regression on a single point:

In PyTorch (run the Colab lab), the identical step is written without any derivatives:

import torch
x = torch.tensor([2.0]); y = torch.tensor([7.0])
w = torch.tensor(1.0, requires_grad=True)
b = torch.tensor(0.0, requires_grad=True)

loss = ((w * x + b) - y) ** 2
loss.backward()                        # fills w.grad, b.grad
with torch.no_grad():
    w -= 0.1 * w.grad
    b -= 0.1 * b.grad
    w.grad.zero_(); b.grad.zero_()     # grads ACCUMULATE between backward calls

Every hand-derived factor above becomes a graph edge; backward() multiplies them for you. 10.4 builds the manual version end-to-end so the automation is never magic.

2. Concept Questions

  1. Why must the PyTorch snippet call w.grad.zero_() after stepping, when the NumPy version has no analogous line?
  2. requires_grad=True is set on w and b but not on x and y. What question is each flag answering?
  3. PyTorch defaults to float32 while NumPy defaults to float64. Give one reason for the choice and one consequence you must respect when comparing against NumPy results.
  4. You get RuntimeError: Expected all tensors to be on the same device. What two lines of your script disagree, and what is the fix?
  5. What does with torch.no_grad(): prevent, and why do both inference and the parameter update itself need it?
Answers
  1. Autograd accumulates into .grad across calls (so gradients can be summed over multiple passes); NumPy locals are recomputed fresh each iteration. Forgetting zero_() is the classic “loss went down but model went crazy” bug — you are summing stale gradients from every previous step.
  2. “Do I need the derivative with respect to this tensor?” We need ∂loss/∂w and ∂loss/∂b (things we update), never ∂loss/∂x (data). Fewer graph nodes = less memory and compute.
  3. Reason: float32 halves memory and doubles GPU throughput, and DL tolerates the precision. Consequence: bitwise agreement with float64 NumPy is impossible — compare with tolerances (rtol=1e-5-ish), and watch accumulated sums (Exercise 2).
  4. The model’s parameters were moved with model.to("cuda") but the input batch stayed on the CPU (or vice versa). Fix: move everything — X = X.to(device) next to model.to(device).
  5. no_grad() stops graph construction. Inference: you don’t need gradients, and building the graph wastes memory (it also lets you feed huge batches). The update: w -= lr * w.grad is itself an op — under grad-tracking it would be recorded into the graph and pollute the next backward pass.

3. Drills & Exercises

Drills

Predict, then run — every reflex here transfers word-for-word to torch.

Exercises (with solutions)

Exercise 1. Hand-computed gradients for a two-layer graph: with h = tanh(W1 @ x), y = W2 @ h, L = sum(y**2), derive ∂L/∂W2 and ∂L/∂W1 in matrix form, implement them in NumPy, and verify every entry against central finite differences. Where does the chain rule force you through tanh'?

Solution

∂L/∂W2 = 2y hᵀ; ∂L/∂W1 = (W2ᵀ · 2y) ⊙ tanh′(W1x) xᵀ, with tanh′(u) = 1 − tanh²(u).

The tanh′ factor is the local slope of the nonlinearity — the term that vanishing/exploding gradients (10.4, 10.7) are made of. In torch, loss.backward() produces exactly dL_dW1, dL_dW2 in W1.grad, W2.grad.

Exercise 2. dtype discipline: PyTorch’s float32 default is a real precision trade. Sum the sequence 1, 0.1, 0.1, … (10⁶ terms, plus the leading 1) in float32 and float64, and compare each to the float64 truth computed pairwise. Then do the same for np.sum on float32 without changing dtype but using math.fsum-style pairwise summation (np.sum already pairs) vs a Python loop. What does this teach you about trusting 7 significant digits?

Solution
Pairwise summation keeps the float32 error near √n · eps (~1e-3 relative at best for eps ≈ 1.2e-7); the sequential loop drifts linearly worse. Torch accumulations on GPU are float32 by default: gradient checks against NumPy float64 must use tolerances ~1e-3–1e-5, never ==, and loss curves plotted from float32 can wobble at the 4th digit — that is the hardware’s arithmetic, not your learning rate.

4. Advanced Information & Pitfalls

  • Grad accumulation is the default, not a bug fix you do once: any training loop needs optimizer.zero_grad() (or zero_grad(set_to_none=True)) before each backward() — unless you deliberately want gradient accumulation over micro-batches.
  • Leaf vs non-leaf: .grad is only populated for leaf tensors created with requires_grad=True. Gradients w.r.t. intermediates need tensor.retain_grad() — rarely what you want; restructure instead.
  • In-place ops on graph tensors (x += ..., x.relu_()) can silently invalidate saved activations and raise “a variable needed for gradient computation has been modified”. Prefer out-of-place ops in layers you write.
  • .item() / .cpu() are device synchronizations: calling them every step to log the loss stalls GPU pipelines — log every k steps, or use loss.detach().
  • Module vs functional: model.train() / model.eval() switch behavior of dropout/batchnorm (10.5) — forgetting eval() corrupts every validation metric.
  • Reproducibility: torch.manual_seed seeds CPU + CUDA, but torch.backends.cudnn.deterministic and dataloader worker seeding are separate switches — a “random” rerun may differ for reasons that are all documented, not mysterious.

Read & Refactor AI Code

This AI-generated training step has three bugs. Diagnose before running the fixed version.

# AI-generated: one training step (will not run here — spot the bugs by reading)
for X_batch, y_batch in loader:
    X_batch, y_batch = X_batch.to("cpu"), y_batch.to("cuda")   # BUG 1
    logits = model(X_batch)
    loss = criterion(logits, y_batch)
    optimizer.step()                                            # BUG 2
    loss.backward()
    running_loss += loss                                        # BUG 3
What’s wrong, and the fix
  1. Device split: data on CPU, model (implicitly) moved to CUDA — or the reverse; every batch raises the device-mismatch error. Move both with the same device variable.
  2. Step before backward: optimizer.step() applies gradients that are zero/stale; the order is zero_grad() → backward() → step().
  3. Graph-carrying accumulator: running_loss += loss keeps the whole graph alive via the loss tensor — memory grows every iteration. Use running_loss += loss.item() (or loss.detach()).
# fixed
for X_batch, y_batch in loader:
    X_batch, y_batch = X_batch.to(device), y_batch.to(device)
    optimizer.zero_grad()
    loss = criterion(model(X_batch), y_batch)
    loss.backward()
    optimizer.step()
    running_loss += loss.item()

5. Advanced Questions

Q1. Reverse-mode autodiff computes all parameter gradients in one backward pass costing ~2× the forward pass, regardless of whether there are 10 parameters or 10 billion. Explain why forward-mode (one directional derivative per pass) is hopeless for training but superior for functions with 1 input and many outputs — and connect this to why JAX/PyTorch offer both modes.

Hint Count passes needed: gradients w.r.t. every parameter (many inputs → one loss) vs a Jacobian with one input row and many output columns.
Solution Reverse mode propagates one adjoint vector backward through the graph: cost O(graph size) total, delivering ∂L/∂θ for all θ at once — exactly DL’s shape of question (scalar loss, millions of parameters). Forward mode carries one tangent direction forward: it yields one column of the Jacobian per pass, so getting all parameter gradients needs P passes — 175 billion passes for a 175B-parameter model. Conversely, for f: ℝ → ℝⁿ (one input, n outputs), forward mode gets the whole Jacobian in one pass while reverse needs n. Tooling follows the question: training = reverse mode; sensitivity analysis of a scalar parameter or implicit-function derivatives (e.g., hyperparameter gradients through a converged solver) often favor forward mode. The deep-learning stack standardized on reverse mode because of this cost argument, not taste.

Q2. Design (in NumPy, live) the semantics of an optimizer step with gradient accumulation over k micro-batches: implement accumulate-then-step for the linear model of Section 1 and show the accumulated update equals the full-batch gradient step exactly when the micro-batch losses are means of equal-sized batches. Where does exactness break (unequal batch sizes, dropout, batchnorm)?

Hint Mean-of-means equals the global mean only when the denominators match; write the two formulas and subtract.
Solution
Exact because every chunk contributes meanᶜ/n·k with equal sizes: (1/k)Σ meanᶜ = global mean. Breaks: (i) unequal chunks — (1/k)Σ meanᶜ ≠ global mean (weight by chunk size); (ii) dropout — each micro-batch samples different masks, so accumulated ≠ single-pass dropout; (iii) batchnorm — batch statistics differ per micro-batch. This is why gradient accumulation for memory-constrained training changes the function being optimized slightly under normalization/dropout, not just its schedule.

7. Summary

  • A tensor = NumPy array + device + dtype + autograd graph; ops and broadcasting transfer 1:1.
  • backward() = your hand chain-rule, automated over a recorded graph; .grad accumulates — zero it before each step.
  • requires_grad marks what you differentiate with respect to; no_grad() stops graph building for inference and updates.
  • float32 is the default: compare against float64 references with tolerances, not equality.
  • Device mismatches and stale graphs (.item(), detach(), eval()) are the day-one operational bugs.
  • Reverse-mode’s one-pass-for-all-parameters cost is the economic reason deep learning is trainable at all.
  • The atom of everything ahead is one linear map + one nonlinearity — up next: 10.2 single-layer networks.
