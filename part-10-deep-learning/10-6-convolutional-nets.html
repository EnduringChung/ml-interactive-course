10.6 Convolutional Neural Networks

A dense layer on images wastes its parameters re-learning the same edge at every position, and throws away the fact that nearby pixels belong together. Convolutions fix both: small kernels, shared across space, composed into features (edges → textures → parts). This page builds the operation by hand in NumPy on scikit-learn’s digits — every concept cell runs live — and the PyTorch training lab runs in Colab.

Tier 3 — CNN training needs a real runtime; the convolution itself is just array surgery, demonstrated live below:

1. Basic Concept

Discrete 2-D convolution (DL’s version is technically cross-correlation — see pitfalls): slide a small kernel \(K\) (\(k \times k\)) over the image, computing each output pixel as a weighted local sum:

\[\text{out}[i, j] = \sum_{u,v} \, \text{in}[i+u, j+v] \cdot K[u, v] + b\]

Two properties make this the right inductive bias for images:

  1. Locality: each output sees only a \(k \times k\) neighborhood — nearby pixels first (vs a dense layer’s global dot product).
  2. Weight sharing: the same \(K\) at every position — translation equivariance (shift input → features shift) with vastly fewer parameters.

Output size: \(\lfloor (n + 2p - k)/s \rfloor + 1\) for input size \(n\), padding \(p\), stride \(s\). Pooling (\(2\times2\) max) halves resolution, buying a little translation invariance on top of equivariance.

Each map is one “channel” a CNN layer would compute — a trained CNN just learns the kernels instead of hand-picking Sobel filters, and stacks layers so layer-2 sees layer-1’s edges.

2. Concept Questions

  1. The dense layer mapping 8×8 digits to 8×8 outputs has how many weights? The 3×3-kernel conv (1 channel in, 1 out) has how many? Which one can transfer from a digit photographed slightly off-center?
  2. Padding “same” vs “valid”: an 8×8 input with 3×3 kernel gives which output sizes? Why do deep stacks need padding (what happens to edge information without it)?
  3. Pooling gives invariance; convolution gives equivariance. State both relations as “if input shifts by δ, then output …”. Where does each property help recognition?
  4. A conv net with all kernels 1×1 is exactly what model? And a conv with kernel size = input size?
  5. Stride-2 convolution vs conv-then-pool: both downsample 2×. What does each do to the information thrown away?
Answers
  1. Dense: 64×64 = 4,096 (+64 bias). Conv: 9 (+1). The conv transfers: its “vertical edge” detector works at any position — the dense layer has no such sharing, so off-center digits are effectively new inputs.
  2. Same: 8×8 (p=1); valid: 6×6. Without padding, each layer shaves k−1 pixels: edge pixels get seen by fewer layers’ outputs (their receptive-field contribution dies) and feature maps shrink until pooling has nothing to pool.
  3. Convolution: input shifts δ ⇒ feature maps shift δ (with interior effects at borders). Pooling: input shifts by less than the pooling window ⇒ pooled output often unchanged. Equivariance lets layer 2 find “edge wherever it is” from layer 1; invariance at the end lets the classifier not care where the digit sits in the frame.
  4. 1×1 kernels = a dense layer applied per-pixel across channels only — a channel mixer / bottleneck (used everywhere in modern architectures). Kernel = input size = a fully-connected layer (weight sharing degenerates — there’s only one position).
  5. Stride-2 conv: a learned linear projection evaluated on a sparse grid — trainable downsampling. Max-pool: fixed nonlinear selection of the local max — no parameters, hard “winner-takes-all” discarding; average-pool softens. Learned stride convs are standard in modern nets; pooling survives mostly as final global-average-pool.

3. Drills & Exercises

Drills

Predict, then run.

Exercises (with solutions)

Exercise 1. Implement conv2d (single channel, valid mode) with loops; verify it against scipy.signal.correlate2d; then state why DL libraries call this “convolution” without flipping the kernel. Time the loop version against the FFT-free vectorized alternative (correlate2d) on a 64×64 input with 3×3 kernel — how many conv layers can your CPU do per second, and what does that imply about training real CNNs in a browser?

Solution
DL “convolution” is cross-correlation: it never flips the kernel. Mathematically the flip matters only for convolution’s algebraic properties (commutativity with the Fourier theorem); for learning, the kernel is free parameters — flipping a learned kernel is absorbed by re-learning, so libraries skip it. Timing: even the C scipy path does only hundreds of single-channel layers/sec; a real net (32 channels × 2 layers × forward+backward × thousands of images) is why CNN training lives on GPUs/Colab, not in Pyodide.

Exercise 2. Hand-conv feature extractor: build a tiny pipeline on a 8×8 digit — conv (vertical edge) → ReLU → 2×2 max-pool → conv (horizontal edge) → ReLU → pool — implemented with your conv2d/correlate2d and NumPy only. Visualize every intermediate map. Then compute the receptive field of one final pixel (how many input pixels influence it) and its stride relative to the input.

Solution
One final pixel’s receptive field, computed stepwise: conv1 → 3, pool1 → \((3-1){\cdot}2+2 = 6\), conv2 (3×3, stride 1) → \((6-1)+3 = 8\), global pool → the whole 8×8 image. Deep stacks grow receptive fields multiplicatively with depth — the geometry that lets layer-5 units see whole objects while stride keeps intermediate grids coarse.

Exercise 3. Shared vs unshared, measured: scikit-learn’s digits (1,797 samples of 8×8), flattened: fit LogisticRegression (dense, unshared, linear) vs a hand-rolled conv-feature pipeline — convolve each image with the 4 kernels from Section 1, pool to 3×3 each, flatten (4×9 = 36 features), then logistic regression on top. Compare 5-fold CV accuracy. The conv features are hand-picked and untrained — what does the gap (or its absence) tell you about what learned kernels add, and where the real win of CNNs lies?

Solution
Hand-picked edge/blur features are competitive with raw pixels on easy digits — because logistic regression on 64 pixels is already a linear-shape-matcher. The CNN’s real win is compositionality at scale: learned kernels arranged in a hierarchy (edges → corners → strokes → digit parts) with weight sharing, trained end-to-end on data where 64 pixels aren’t enough (MNIST/CIFAR — the Colab lab shows the gap properly). Fixed features top out; learned hierarchical features scale with data — the exact argument of 10.10’s “structure + data” quadrant.

4. Advanced Information & Pitfalls

  • It’s cross-correlation: DL convolutions don’t flip kernels. Consequence-free for training, but confusing when porting signal-processing filters or implementing deconvolution.
  • Layout chaos: PyTorch is NCHW (batch, channel, height, width); TensorFlow defaults NHWC. A (8, 8) single image needs shape (1, 1, 8, 8) in torch — “missing channel dimension” is the day-one error.
  • Border effects: without padding, valid convolutions shrink maps and underweight border pixels (they appear in fewer receptive fields); same padding mitigates but pads with zeros — reflect/replicate padding is kinder for images with meaningful borders.
  • Flatten loses spatial layout: flatten → dense after convs works but discards the 2-D arrangement; global average pooling is the modern replacement (fewer params, translation-tolerant).
  • Small data + big CNN = instant overfit (10.5): augmentation (shifts/rotations) is not optional on datasets of hundreds; weight sharing is a prior, not a guarantee.
  • Receptive field ≠ resolution: stride/pooling grow receptive fields but sample them coarsely — dilated convolutions grow the field without losing grid density (segmentation’s standard trick).

Read & Refactor AI Code

This AI-generated conv layer (NumPy) has three bugs. Find them before running the fixed version.

What’s wrong, and the fix
  1. Wrong output shape: valid mode must produce (H−k+1, W−k+1) = (6, 6); claiming (8, 8) fills only the interior and leaves a silently-zero border — fake “features” that the next layer will happily consume.
  2. Copy-paste batch bug: imgs[0] inside the loop gives every image the first image’s feature maps — the classic AI copy-paste error, invisible because shapes are all correct.
  3. Off-by-one write: storing at i + 1, j + 1 shifts every feature map down-right by a pixel; after flattening, the model sees displaced edges as real spatial structure.
The general lesson: hand-rolled array code must assert shapes — NumPy slicing truncates silently, and a wrong-but-shaped output is worse than an exception.

5. Advanced Questions

Q1. Equivariance, precisely: prove that convolution with kernel \(K\) commutes with integer translations — \(T_\delta(C(x)) = C(T_\delta(x))\) for the interior of the output — and identify exactly where the proof breaks (borders; stride; pooling). Then show max-pooling is not equivariant but is approximately invariant for shifts smaller than the pool window. Why do CNN stacks pair the two in this order?

Hint Write both compositions as index sums; the kernel slides with the image. For pooling, compare argmax sets under small shifts.
Solution Translation by δ: \(C(T_\delta x)[p] = \sum_u K[u]\,x[p + u - \delta] = (C x)[p - \delta] = T_\delta(Cx)[p]\) — kernel and image translate together, so outputs translate (valid-mode interior). Breaks: (i) borders — the sum clips differently at edges, so equivariance is approximate there; (ii) stride s — outputs exist only on a subgrid, translation by non-multiples of s has no corresponding output shift; (iii) pooling — max over a window: shifting input moves the max but if it crosses a window boundary the output changes non-uniformly (not a shift), yet for sub-window shifts the same max usually survives — approximate invariance. The stack order exploits both: convolutions carry position information equivariantly upward (layer 2 can reason about arrangement), while pooling locally forgets small displacements so downstream layers see stabler features; only at the top does full invariance (global average pool) feed the classifier.

Q2. The 1×1 bottleneck: a residual block conv3×3(C→C) → conv3×3(C→C) costs \(2C^2 \cdot 9\) params; the bottlenecked version 1×1(C→C/4) → 3×3(C/4→C/4) → 1×1(C/4→C) costs… compute both for C = 256, verify numerically with a parameter-count function, and explain what the 1×1 convs are doing semantically (channel mixing/pca-style projection — connect to 9.2 PCA). When is the bottleneck not a good trade?

Hint Bottleneck ≈ 2·C²/4·… just compute. The 1×1 layers are linear maps across channels at each pixel — exactly PCA-whitening’s job if the data cooperated.
Solution
Standard: 2·256²·9 ≈ 1.18M; bottleneck: 2·(256·64) + 64²·9 ≈ 69K — 17× cheaper, which is why ResNet-50’s deeper bottlenecked blocks cost less than ResNet-34’s plain ones. Semantically, the 1×1s are per-pixel linear maps across channels — compressing to a 64-dim subspace where the 3×3 spatial mixing happens, then re-expanding: PCA-flavored dimensionality (9.2) with learned components. Bad trade when channels are already few (C = 32: bottleneck of 8 strips capacity), or when the task needs full-width interactions in every 3×3 (fine-grained textures) — compression is a prior that locality-of-information lives in a subspace.

6. Complex Questions

C1 (× 10.5 augmentation × 9.2 PCA). Weight sharing bakes in translation equivariance; augmentation bakes in more invariances (rotation, shear). On the digits data, quantify the overlap: augment training images with small rotations, re-run Exercise 3’s two pipelines, and measure how much of the augmentation gain the conv-feature pipeline already captures (hand kernels are themselves edge-detectors). Hypothesize before measuring: does augmentation help the raw-pixel pipeline more than the conv pipeline? Why does that ordering reveal what each representation already “knows”?

C2 (× 10.9 attention × 10.7). Convolutions hard-code locality; attention is global from layer 1. Sketch (no training) the compute cost of one layer over a 224×224 image for (a) a stack of 3×3 convs reaching a global receptive field, (b) single-head self-attention over all pixels. Compute parameter counts and FLOPs-as-matrix-sizes for C = 64. Then state the modern synthesis (local conv stem + attention blocks) as a cost/benefit argument rather than a fashion choice — and why image transformers still keep patch embeddings (10.9’ quadratic term, tamed).

7. Summary

  • Convolution = locality + weight sharing: translation-equivariant features with orders-of-magnitude fewer parameters.
  • Output shape \(\lfloor(n+2p-k)/s\rfloor+1\); padding preserves borders; pooling adds local invariance on top of equivariance.
  • 1×1 convs are per-pixel channel mixers — bottleneck blocks trade width for depth cheaply.
  • NumPy slicing truncates silently: hand-rolled convolutions must assert patch shapes.
  • Hand-picked kernels get you surprisingly far on easy images; learned hierarchical kernels are what scale — that’s the data+structure argument of 10.10.
  • Images stack spatially; sequences need memory — next: 10.7 recurrent neural networks.
