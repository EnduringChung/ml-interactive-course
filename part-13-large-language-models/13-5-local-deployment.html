13.5 Local Deployment

13.4 ended with “open weights: you can run it yourself.” This page is the how: the local-inference stack (Ollama, llama.cpp, vLLM, Hugging Face), the quantization math that makes 7B–70B models fit in consumer VRAM, and the hardware arithmetic that decides what runs where. The heavy lifting — actually loading and running a model — happens in the companion Colab lab; the concepts (quantization, memory budgets, bandwidth limits) run live here.

Tier 3 — model inference does not run in this browser. Concept cells below are live NumPy; the full deployment lab runs in Colab:

1. Basic Concept

Why run locally: privacy (data never leaves the machine — clinical notes, proprietary code), cost at scale (API per-token fees vs a one-time hardware cost), offline/air-gapped operation, and the prerequisite for fine-tuning (13.6). The trade: you supply the hardware and the quality ceiling is your GPU.

The stack, simplest to most control:

Tool What it is You reach for it when
Ollama one-command model runner (llama.cpp wrapped) you want to use a model, not engineer one
llama.cpp the C++ inference engine (GGUF format) you want minimal deps, CPU+GPU hybrid, or to embed
Hugging Face transformers the Python library (training + inference) you want to program against models
vLLM high-throughput serving engine (PagedAttention) you’re serving many users, not one

Quantization — the core trick. A float16 weight is 2 bytes; an int8 weight is 1 byte; int4 is 0.5. Quantization maps each weight (or group of weights) from a float range to an integer grid: \(w \approx s \cdot (q - z)\), where \(s\) is the scale, \(q\) the integer, \(z\) the zero-point. The model gets 2–4× smaller and faster (integer math, less memory traffic) at a small quality cost. The formats: GGUF (llama.cpp’s file format, Q4_K_M etc. — per-block scales), GPTQ (post-training quantization, layer-by-layer error compensation), AWQ (activation-aware — protects the weights that matter most), bitsandbytes (int8/int4 for transformers, the Colab path).

The memory budget — the number that decides everything:

\[\text{VRAM} \approx \underbrace{2 \text{ bytes} \times N}_{\text{weights (fp16)}} \; \text{or} \; \underbrace{b \times N}_{\text{quantized}} + \underbrace{\text{KV-cache}}_{\propto T} + \underbrace{\text{activations + overhead}}_{\sim 1\text{–}2 \text{ GiB}}\]

A 7B model in fp16 needs ~14 GiB — just over a 12 GiB laptop GPU; in int4, ~3.5 GiB — comfortable. A 70B model in int4 needs ~35 GiB — a 48 GiB A6000 or an 80 GiB A100, or a multi-GPU setup. Worked example — the quantization math, live:

Per-group scales (a scale per 32 weights instead of one per tensor) cut the error dramatically — the tensor-wide scale is dominated by a few large outliers, and per-group scales let each region use the full integer range. This is why GGUF’s Q4_K_M (per-block scales with a 6-bit scale-of-scale) is the default “small but good” format.

2. Concept Questions

  1. Why is generation (not pretraining) the memory-bandwidth-bound phase? Compute the arithmetic intensity of one decoding step: the model reads every weight once to produce one token. What does that imply for tokens/second on a given GPU?
  2. Per-group quantization beats per-tensor because of outlier weights. Why do transformers have outlier dimensions, and what does AWQ do differently from plain per-group quantization?
  3. The memory budget has a KV-cache term that grows with context length \(T\). Why does a 128k-context model need more VRAM at inference even if you only ever send 1k-token prompts — and what is the mitigation?
  4. Ollama’s Q4_K_M and a bf16 file of the same model differ by ~4× in size. Where does the quality difference actually come from — the number of bits, or how the bits are spent?
  5. You want to run a 32B model on a 24 GiB consumer GPU. fp16 needs 64 GiB, int8 needs 32 GiB, int4 needs 16 GiB. Which do you pick, and what two other knobs (besides bits-per-weight) can close the gap?
Answers
  1. Decoding reads all \(N\) weights from VRAM to compute one token’s logits: \(2N\) FLOPs per token against \(2N\) bytes of weight traffic — arithmetic intensity ≈ 1 FLOP/byte, far below any GPU’s compute/bandwidth ratio (an H100: ~1000 TFLOPs vs ~3 TB/s → ratio ~300). So decoding speed ≈ (memory bandwidth) / (bytes per token) — the GPU’s compute units are mostly idle, waiting on memory. Consequence: tokens/second scales with bandwidth, not FLOPs — which is why quantization (fewer bytes) directly buys speed, and why CPU inference (lower bandwidth) is slow even with spare compute.
  2. A few embedding dimensions carry systematically large activations (“massive activations”); the weights interacting with them must stay precise or every token’s output is corrupted. Plain per-group quantization treats all groups alike; AWQ measures activation magnitudes and protects the weight columns with the largest activation overlap (scaling them up before quantizing so they land on the finer part of the grid). Same bits, better spent.
  3. The KV-cache is allocated for the maximum context length — the engine reserves memory for a 128k sequence whether you use 1k or 128k, because it can’t know in advance. Mitigations: context-length caps at load time, PagedAttention (vLLM — allocate cache in blocks as needed, like virtual memory), and sliding-window attention (the model only uses a window anyway, 13.2 Exercise 3).
  4. How the bits are spent. Per-block scales, mixed precision (keep sensitive layers at higher bits), and activation-aware protection (AWQ) all buy quality at fixed bit-width — the difference between a naive int4 and Q4_K_M is larger than the difference between naive int4 and naive int8. Quantization is an allocation problem, not just a precision problem.
  5. int4 (16 GiB) leaves headroom. The other knobs: (i) offload — keep some layers on CPU/RAM and stream them (llama.cpp’s -ngl flag; slower but fits), (ii) sharding — split the model across two GPUs (or GPU+CPU) so no single device holds it all. Also: smaller context allocation (Q3) and accepting a smaller model (a 14B int4 at 7 GiB often beats a 32B int4 at 16 GiB on quality-per-latency for single-user use).

3. Drills & Exercises

Drills

Predict, then run.

Exercises (with solutions)

Exercise 1. Implement group-wise int4 quantization with the GGUF-style twist: per-block scales and a per-block scale-of-scale (the “K” in Q4_K_M — the scale itself is quantized to 6 bits). Quantize the Section 1 weight matrix, measure the error vs plain per-group int4, and state the memory cost of the extra metadata (per 32-weight block: 0.5 bytes/weight + 2 bytes scale + 2 bytes scale-of-scale ≈ 0.56 bytes/weight — why “Q4” is really ~4.5 bits).

Solution
The scale-of-scale costs 4 bytes per 32-weight block — 0.125 bytes/weight on top of the 0.5 bytes/weight of the int4 values, so “Q4” is really ~4.5–5 bits/weight once metadata is counted. The error reduction is modest on this synthetic matrix (real weight distributions with outliers benefit more); the point is the accounting: quantization formats are a bit-budget, and metadata is part of the budget. Always compute effective bits/weight as (values + scales + zero-points) / weights — the marketing number (Q4) and the file-size number differ by ~15%.

Exercise 2. The bandwidth-bound speed model: a 7B int4 model (3.5 GB weights) on a GPU with 1 TB/s bandwidth should decode at ~285 tokens/s by the drill-1 arithmetic. But real llama.cpp on a 4090 gets ~60–100 tokens/s. List the three reasons the simple model overpredicts, then compute what fraction of peak bandwidth a well-tuned kernel actually achieves, and state what that implies for choosing between “more quantization” and “better kernels.”

Hint</ The simple model assumes: weights are read once, nothing else competes for bandwidth, and the kernel achieves peak. Reality: dequantization compute, KV-cache traffic, and kernel efficiency all take their cut.
Solution
Three reasons for the gap: (i) dequantization compute — int4 weights are unpacked to float in registers; the unpacking ALU work and the extra register pressure slow the memory pipeline (the kernel is not purely bandwidth-bound at these tiny per-token matmuls); (ii) KV-cache traffic — every step also reads/writes the KV-cache (growing with \(T\)), competing for the same bandwidth; (iii) kernel efficiency — small matmuls (one token × 4096-dim layers) don’t saturate HBM; achieving 80–90% of peak needs large batched GEMMs, which single-user decoding doesn’t have. Implication: at ~25% of peak, the first 2× of speedup comes from better kernels (batching, fused dequant, tensor-core int4 GEMMs), not more quantization — which is why the field ships both (quantized formats and optimized runtimes). The crossover: once kernels are near peak, quantization is the only lever left — the two strategies are sequential, not either/or.

Exercise 3. Size the deployment: you have a 24 GiB GPU and want the best possible model for (a) a single-user chat with 8k context, (b) a RAG server handling 50 concurrent users with 4k contexts. For each, compute the memory budget (weights + KV-cache + overhead), pick a quantization level for 7B / 14B / 32B / 70B candidates, and state which you’d deploy and why. Use the drill-2 formula with \(h_{kv} = 8\), \(d = 4096\) (7B/14B) or \(8192\) (70B), \(L = 32/32/80\).

Solution
  1. Single-user: 32B int4 (~16 + 0.5 + 1.5 ≈ 18 GiB) or 14B int8 (~14 + 0.25 + 1.5 ≈ 16 GiB) both fit; 70B int4 (~35 GiB) doesn’t. Pick 32B int4 — quality per user is what matters when there’s one user, and the KV-cache at 8k is small. (b) 50 concurrent: the KV-cache term explodes — 50 users × 4k context × 32 layers × 8 KV heads × 4096 × 2 (K+V) × 2 bytes ≈ 41 GiB per 7B model — the cache, not the weights, is the constraint. Pick 7B int4 and cap context/users, or move to a serving engine (vLLM’s PagedAttention shares cache across users with common prefixes). The general lesson: single-user deployment is weight-bound; multi-user deployment is cache-bound — the two regimes size completely differently, and the serving stack (batching, paged cache) matters more than the model choice in the second.

4. Advanced Information & Pitfalls

  • “It runs” ≠ “it runs well.” A 70B int4 on a 48 GiB GPU works; at 5 tokens/s with 200 ms/word latency it’s unusable for interactive chat. Always benchmark your prompt lengths and your concurrency before committing hardware.
  • Quantization quality is task-dependent. A Q4 model loses ~0.1–0.3 perplexity on average — invisible on chat, visible on precise multi-step reasoning or rare-domain knowledge. Evaluate on your task’s data, not on the format’s marketing.
  • Outlier dimensions break naive quantization — a few large-magnitude weights force a coarse per-tensor scale. If you ever quantize yourself: per-group scales, and consider keeping the outlier dims in fp16 (mixed precision, as AWQ/GGUF do).
  • Model files are code-adjacent trust objects. A GGUF from an untrusted source is a multi-GB binary you’re loading into a tool with filesystem access. Use official repos (Hugging Face verified, Ollama’s model library) and check hashes.
  • CPU inference is a different trade: llama.cpp on a Mac with unified memory can run 7B int4 at ~30 tokens/s with zero GPU — the memory is shared, the bandwidth is decent, and the laptop stays silent. For many users this is the best deployment, not a compromise.
  • The KV-cache is the silent cost: at long contexts it exceeds the weights (Exercise 3b). If your use case is long documents, budget for the cache first — a 7B model at 128k context needs more VRAM than a 14B model at 8k.

Read & Refactor AI Code

This AI-generated quantization function has three bugs. Diagnose before running the fixed version.

# AI-generated: quantize a weight matrix to int4 (will not run here — spot the bugs)
def quantize(W, bits=4):
    qmax = 2 ** bits - 1                    # BUG 1
    s = W.max() / qmax
    q = np.round(W / s)
    return s * q                             # BUG 2

def dequantize(q, s):
    return s * (q - 128)                     # BUG 3
What’s wrong, and the fix
  1. Wrong range for signed int4: 2**4 - 1 = 15 treats int4 as unsigned [0, 15]. Signed int4 is [-8, 7] (or [-7, 7] symmetric) — the scale must be computed from the actual min/max, and the rounding clipped to the signed range. As written, negative weights all quantize to 0.
  2. No clipping: np.round(W / s) can exceed the integer range (any weight above qmax * s — and s is set by the max, so values near the max round to exactly qmax, but the unsigned range means the top half of the grid is wasted on sign). Clip to [-qmax, qmax] after rounding.
  3. Hardcoded 128 zero-point: q - 128 assumes uint8’s zero-point; for int4 the zero-point is 0 (symmetric) or computed from the data (asymmetric). The dequantization must use the same convention as the quantization — and the scale must be passed consistently.
# fixed
def quantize(W, bits=4):
    qmax = 2 ** (bits - 1) - 1               # signed range [-7, 7]
    s = W.max() / qmax
    q = np.clip(np.round(W / s), -qmax, qmax)
    return q, s

def dequantize(q, s):
    return s * q                             # symmetric: zero-point is 0

5. Advanced Questions

Q1. Why is decoding bandwidth-bound but pretraining compute-bound? Compute the arithmetic intensity of both: pretraining processes a batch of \(B\) tokens with the same weights (weights read once per batch), decoding processes 1 token. Then state the architectural consequence — why tensor cores matter for training but barely for single-user decoding, and why batching users (continuous batching, vLLM) is the serving-side fix.

Hint Arithmetic intensity = FLOPs / bytes of memory traffic. Compare \(B\) tokens vs 1 token against the same weight read.
Solution Pretraining: one weight read serves \(B\) tokens (say \(B\) = 4M tokens in a large run’s micro-batches — even \(B\) = 512 gives intensity \(2N \cdot B / 2N = B\) FLOP/byte ≈ 512, well above the ~300 ratio — compute-bound, tensor cores saturated). Decoding: one weight read serves 1 token — intensity ≈ 1, memory-bound, tensor cores idle. Consequence: training efficiency is about FLOPs utilization (MFU — the 50% figure in the drill); single-user decoding efficiency is about bandwidth. The serving fix is continuous batching: pack many users’ tokens into one GEMM — the weights are read once per batch of users, restoring compute-bound economics (intensity = number of users in flight). This is why vLLM/TGI can serve 50 users at aggregate speeds near the pretraining hardware’s potential, while naive one-user-at-a-time serving wastes 75% of it (Exercise 2). The same hardware, two regimes — the batch size is the dial between them.

Q2. The quantization error → quality relationship: using the Section 1 matrix, measure how quantization error scales with bits (2, 3, 4, 8, 16) and fit the exponent (error ∝ 2^(−bits)?). Then state why the perplexity impact is sublinear in the weight error (the network averages over thousands of weights — errors partially cancel), and why the worst case (outlier dimensions) dominates the tail of the quality loss.

Hint Fit log(error) vs bits — the slope is the exponent. Then think about error accumulation across a 32-layer network with 4096-dim dot products.
Solution
Error halves per bit (slope ≈ −1 in log2) — each bit buys one binary digit of precision, as expected. But perplexity impact is sublinear in weight error: a dot product of 4096 terms with independent quantization errors has error growing as \(\sqrt{d}\) while the signal grows as \(d\) — the relative error shrinks with dimension, and across 32 layers the errors partially cancel (they’re zero-mean). That’s why int4’s naive error looks scary in isolation but costs only ~0.1–0.3 perplexity in practice. The exception: outlier dimensions — a few weights with 10–100× the typical magnitude. Their quantization error is large and they interact with large activations (every token touches them), so they don’t average away — they dominate the tail of the quality loss. This is the entire motivation for AWQ and mixed-precision formats: protect the outliers, quantize the rest aggressively.

6. Complex Questions

C1 (deployment × 10.1 tensors × 13.4). The KV-cache is a tensor that grows every decoding step — a define-by-run shape change. Trace the memory lifecycle: pre-allocated max-context buffer (llama.cpp) vs PagedAttention’s block allocator (vLLM) vs the naive torch.cat approach (OOMs at long contexts). State which 10.1 concept each design is an instance of, and why the naive approach fails the 13.2 Exercise 3 memory arithmetic.

C2 (deployment × 13.6 × 13.3). Fine-tuning a local model (LoRA, 13.6) has its own deployment story: the base model is int4 on the GPU, the LoRA adapter is fp16, and the serving engine must fuse or compose them. Compute the memory cost of a 7B int4 base + 50M-param fp16 LoRA adapter, state whether the adapter changes the quantization story (it doesn’t — why?), and describe the inference-time composition (W + BA applied per forward) and its cost.

7. Summary

  • Local deployment: Ollama (use it) → llama.cpp (embed it) → transformers (program it) → vLLM (serve it).
  • Quantization: \(w \approx s(q - z)\); per-group scales beat per-tensor because of outlier weights; metadata is part of the bit budget (“Q4” ≈ 4.5–5 bits/weight).
  • The VRAM budget = weights + KV-cache + overhead; single-user is weight-bound, multi-user is cache-bound.
  • Decoding is memory-bandwidth-bound (intensity ≈ 1 FLOP/byte); pretraining is compute-bound (intensity ≈ batch size) — batching users is the serving-side fix.
  • Quantization error halves per bit but perplexity impact is sublinear (errors average over dimensions) — except at outlier dimensions, which AWQ/mixed-precision protect.
  • “Runs” ≠ “runs well”: benchmark your prompt lengths, concurrency, and task before buying hardware.
