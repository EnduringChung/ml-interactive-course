0.5 Data Splitting

Every model in this course will be judged by one rule: performance on data it did not see during training. The mechanics of splitting data seem trivial — and that’s exactly why leakage bugs are so common. This page drills the mechanics so they’re automatic before Part 2 builds models on top of them.

1. Basic Concept

The test set estimates how a model performs on new data. The core failure mode is leakage: any information from the test set (or from future data) influencing the training process inflates that estimate.

2. Concept Questions

  1. Why must the test set be used once, at the end — what exactly is lost if you peek repeatedly?
  2. What does stratify=y protect you from, and when is it useless?
  3. Why does random_state matter in research code even when results “should” be stable?
  4. In 5-fold CV, how many times is each sample used for validation, and how many times for training?
  5. Your test R² is better than your training R². Give one benign explanation and one suspicious one.
Answers
  1. Repeatedly peeking at test performance and making choices (features, hyperparameters, stopping) based on it trains on the test set through you: the estimate stops being out-of-sample and becomes optimistically biased. The test set’s value is spent by adaptation.
  2. It preserves class proportions across splits — essential for rare classes (a 2% class can be absent from a small test split). Useless/unnecessary for regression (continuous y), and it can’t fix too small data: if a class has fewer members than folds, even stratified splitting fails.
  3. Same seed → same split → run-to-run reproducibility, which is what makes bug fixes, reviewer requests, and controlled comparisons possible. Unseeded splits confound “different partition” with “different method.”
  4. Exactly once for validation; K−1 = 4 times for training (in different combinations).
  5. Benign: the test split happens to be easy, or training metrics are computed on a regularized objective (e.g. penalized loss) while test R² is unpenalized. Suspicious: leakage — test information reached training (scaled together, duplicated rows, feature derived from the outcome). Investigate, don’t celebrate.

3. Drills & Exercises

Drills

Exercises (with solutions)

Exercise 1. Simulate a small classification dataset (500 samples, 2% positives), split it badly (no stratify, seed chosen “unluckily”) and well (stratify). Report positives in each test set. Then quantify: repeat the unstratified split 500 times and report the range of positive counts in the test set.

Solution
A test set with zero positives makes recall, AUC, and AUPRC literally undefined. Stratification is not cosmetic.

Exercise 2. Write a 5-fold CV loop by hand (KFold + explicit fit/predict on a LinearRegression) for the synthetic regression data from Section 1, collecting validation R² per fold. Report the mean and the standard deviation across folds — then explain why that SD, not just the mean, matters.

Solution
The mean estimates expected performance; the SD across folds estimates how stable that number is. Mean ± SD ≈ 0.85 ± 0.06 and mean ± SD ≈ 0.85 ± 0.30 are very different claims about your model — an unstable CV is a red flag for high variance (see 4.4 Bias–variance trade-off).

Exercise 3 — the leakage lab. Build a dataset where one feature is derived from the outcome (leaky = y + noise). Compare (a) a model trained with the leaky feature vs (b) without, using a proper split. Then do it “wrong”: scale X on the full dataset before splitting. Which comparisons change? Quantify each difference.

Solution
Read the results: the leaky feature produces near-perfect accuracy by construction — the single most common way “too good to be true” results reach publication. Pre-split scaling is the same crime at lower dose: test-row means/variances shaped the training inputs.

4. Advanced Information & Pitfalls

  • Leakage taxonomy: (1) feature leakage — a column derived from y (outcomes aggregated into features, “post-treatment” variables); (2) preprocessing leakage — scaling/imputation/feature selection fitted before the split; (3) duplication leakage — the same patient/sample appearing in train and test; (4) temporal leakage — shuffling time series so the model trains on the future.
  • The fix for (2) is always the same shape: fit the transformer inside the training fold only — StandardScaler().fit(X_tr), then .transform(X_te). In pipelines: make_pipeline(StandardScaler(), Ridge()) + cross_val_score does this mechanically and correctly.
  • Duplicate rows before splitting: drop_duplicates / group-aware splitting by patient ID (GroupKFold) — not by row.
  • test_size semantics: float = proportion, int = absolute count. Tiny test sets (n < ~30 per class) make every performance estimate mostly noise (4.1 The generalization problem).
  • shuffle=False is the correct default for time-ordered data — train_test_split shuffles by default, which is wrong for temporal splits.
  • Reproducibility chain: seed the split and any stochastic model; a notebook is only reproducible if every source of randomness is pinned.

5. Advanced Questions

Q1. A reviewer asks why your cross-validation used shuffle=True, random_state=42. Justify both choices, and explain when shuffle=True would be wrong.

Hint What order were the rows in? What does an unshuffled KFold fold look like if the table is sorted by group or by time?
Solution shuffle=True protects against order artifacts: real data frames are often sorted (by site, date, or outcome), and unshuffled KFold then makes folds that are systematically different from each other — e.g. sorted-by-class data can place an entire class in one fold, making it a training-only class for other folds. random_state makes the shuffling deterministic so the estimate is reproducible and comparable across code changes. shuffle=True is wrong when row order carries information: time series (train must precede test — use TimeSeriesSplit), spliced biological batches where you want to generalize to a new batch (use GroupKFold/leave-one-batch-out instead), and grouped data where rows share a subject (shuffle splits subject’s rows across train/test — leakage). The seed is part of the protocol, like the test set itself.

Q2. Your test set has 200 samples and true accuracy 80%. What is the standard error of the measured accuracy, and what does that imply about differences of 1–2 points between two models’ test scores?

Hint Binomial SE = √(p(1−p)/n). Compute it for p = 0.8, n = 200.
Solution SE = √(0.8·0.2/200) = √0.0008 ≈ 0.028 (2.8 percentage points). Two models measured 81% vs 83% on this test set differ by ~0.7 SE — indistinguishable from partition noise. Implications: (1) report uncertainty with test metrics, not just points; (2) prefer cross-validation for comparisons (averages over splits); (3) reserve the biggest test set you can afford; (4) resist leaderboard-grade conclusions from small test sets. This is the bridge to 4.1 The generalization problem and 4.3 Cross-validation.

6. Complex Questions

C1 (splitting × 0.4 EDA). Construct a dataset where the test set’s marginal distribution differs visibly from training’s (e.g. sample y-dependent data, then split unstratified). Plot both test histograms. Then explain, quantitatively, how a covariate-shifted test set changes the meaning of every metric you compute on it — and why stratify/shuffling fixes the estimation but not a genuinely shifted deployment population.

C2 (splitting × 1.5 Resampling). Repeated train/test splitting (50 random 80/20 splits) gives a distribution of test R². Compare its spread to the K-fold spread from Exercise 2. Which estimator has lower variance here, and what does each split in the repeated scheme share with the others that K-fold handles differently? (This previews why repeated CV and bootstrap (4.5 Bootstrap) exist.)

7. Summary

  • Test data answers one question — “how does this do on new data?” — and must be spent once.
  • train_test_split(test_size, random_state, stratify=y): stratify classes, seed everything.
  • K-fold: every sample validated once; report mean and across-fold SD.
  • Leakage has four faces: y-derived features, pre-fit preprocessing, duplicate subjects, shuffled time.
  • The universal fix: fit preprocessing inside training folds — or just use a Pipeline.
  • Small/imbalanced test sets produce undefined metrics and noisy numbers; SE of accuracy ≈ √(p(1−p)/n).
  • Part 0’s toolkit is complete. Next, Part 1 builds the statistical language — centers, spread, probability, and inference — that turns those splits and plots into claims: 1.1 Descriptive statistics.
