8.6 Multiclass SVM

Binary SVMs answer “this class or that one?” — real problems ask “which of k?” Two standard extensions compose binary machines into multiclass classifiers: one-vs-rest (OvR: k machines, each against everyone) and one-vs-one (OvO: k(k−1)/2 machines, each on a pair). SVC runs OvO internally; knowing what that means for scores, calibration, and imbalance is this page’s job.

Tier 1 — every cell below runs live.

1. Basic Concept

OvR: train fₖ(x) = “class k vs not-k” for each k; predict argmaxₖ fₖ(x). OvO: train f_{kl} on classes k and l only; predict by pairwise-vote majority (decision_function returns the k(k−1)/2 vote margins).

2. Concept Questions

  1. OvR with 1% positive class: what happens to each rest-vs-one machine’s training balance, and which page’s remedy applies to each binary subproblem?
  2. OvO trains on only 2/nᵏ-ish of the data per machine. Why is that fine for SVC specifically (name the scaling behavior it dodges)?
  3. decision_function for SVC multiclass returns 3 scores for 3 classes. Are these probabilities? Are they comparable across rows?
  4. When do OvR and OvO disagree most, and give one dataset property favoring each.
  5. Your 10-class problem needs calibrated probabilities for downstream cost decisions. What is the two-step pipeline, and which model class makes it trivial?
Answers
  1. Each OvR machine sees ~1% positives vs 99% rest — the imbalanced binary problem k times over. Apply class weights / stratified folds / PR-metric evaluation per machine (3.1); the argmax across machines then compares scores trained on different balances — a known OvR wart.
  2. SVC’s dual training scales roughly between n² and n³; restricting each machine to 2·(2n/k) rows slashes total cost for large k — OvO is the scaling-friendly choice for kernel-SVC multiclass (sklearn’s default for exactly this reason).
  3. No and no. They’re pairwise vote margins in arbitrary per-machine scales (each pair’s SVM has its own w‖); comparable within a row for voting, not calibrated probabilities across rows or samples (8.5’s probability caveat, k-fold worse).
  4. Disagreement peaks near class boundaries and under imbalance (OvR’s rest-class dominates its machine; OvO’s votes fragment). Favor OvO: large k with kernel-SVC (compute); favor OvR: few classes, per-class interpretability (“class k’s own machine”), or sparse outputs.
  5. Model that emits real per-class probabilities (multinomial logistic — softmax, 3.3 extension) then calibrate + apply costs (3.7); SVM route: OvR/OvO scores → probability calibration (extra layer, extra caution).

3. Drills & Exercises

Drills

Predict, then run.

Exercises (with solutions)

Exercise 1. OvR vs OvO vs multinomial, three ways: fit LinearSVC(OvR), SVC(OvO), and LogisticRegression(multinomial softmax) on a 5-class Gaussian problem; compare CV accuracy, fit time, and prediction agreement rates. Then answer: where do OvR and softmax disagree most — and which disagreement is “probability-shaped” vs “margin-shaped”?

Solution
Softmax differs from the SVMs on confidence geometry: it’s the one producing comparable per-class probabilities, so its “disagreements” with margin models concentrate where probabilities (not margins) would rank classes differently — near boundaries between close pairs. Margins answer “which side,” softmax answers “how much of each” — related questions, different answers, choose per downstream need.

Exercise 2. Imbalance across 4 classes (1%, 4%, 15%, 80%): compare SVC-OvO with and without per-pair class_weight="balanced" by macro-F1 and per-class recall (3.1). Which classes get sacrificed by default, and does balancing fix every class or shift the sacrifice? Write the deployment rule for imbalanced multiclass problems.

Solution
Unweighted OvO sacrifices the 1% class almost entirely (recall ≈ 0) and leans on the 80% class; class_weight="balanced" rescales each pair’s penalties, rescuing rare-class recall at the cost of the majority’s precision — recall mass moves, it doesn’t appear. Deployment rule: imbalanced multiclass needs per-class recall targets set by the costs of missing each class, encoded via class weights (or resampling), and evaluated by macro-averaged metrics — never by accuracy or micro-F1 alone.

Exercise 3. Codebook features vs native multiclass: build a 6-class problem where classes sit on a hierarchy (2 supergroups × 3 subclasses). Compare (a) flat 6-class SVC, (b) a two-level strategy: supergroup SVM → subclass SVC within predicted supergroup. Report flat vs hierarchical accuracy (overall and per-subclass). When does the hierarchy help (signal lives at the top level), when does it double-punish (early error propagates), and what does this preview about structured prediction?

Solution
The hierarchy helps when the top split is real and clean (supergroups well separated) — each subproblem becomes easier; it hurts when supergroups overlap, because one wrong top-level call guarantees a wrong subclass — error compounding. Same trade as any structured/sequential prediction: decompose only along genuinely strong boundaries, and measure the top level’s accuracy before trusting the cascade.

4. Advanced Information & Pitfalls

  • decision_function shape is the tell: (n, k) → OvR scores (LinearSVC, LogisticRegression); (n, k(k−1)/2) → OvO votes (SVC). Code that assumes k columns breaks silently when swapping SVC/LinearSVC.
  • OvR’s scale non-comparability: each rest-machine has its own w scale; argmax compares apples to slightly different apples — probability calibration or shared-margin formulations fix it if scores must travel.
  • OvO’s vote ties: with even class counts, votes can tie; sklearn breaks them by a deterministic rule — for audit-sensitive applications, inspect decision_function rather than trusting the tiebreak.
  • Compute crossover: LinearSVC OvR ≈ k fast primal fits (scales to big n); SVC OvO = k(k−1)/2 dual fits on small pairs (scales to big k with kernels) — the reason SVC defaults to OvO.
  • class_weight semantics per strategy: OvR applies it per binary machine; OvO per pair — the effective weighting of rare classes differs; verify with per-class recalls, not the API name.
  • Calibration multiclass: calibrating k OvR machines independently doesn’t calibrate the argmax distribution — use proper multiclass calibration if probabilities matter (3.7).

This AI-generated multiclass pipeline has three bugs. Run, diagnose, fix.

What’s wrong, and the fix
  1. Vote margins ≠ probabilities: SVC’s decision_function returns k(k−1)/2 pairwise scores; calling them class probabilities misstates both count and meaning. Use probability=True (Platt) — or a softmax model.
  2. Flat accuracy on 25:5:1 imbalance hides total sacrifice of class 2 — macro-F1 + per-class recall (Exercise 2).
  3. Vote margins aren’t cross-row comparable confidence: each pair-machine normalizes differently. Calibrated probabilities (or per-row softmax-style rescaling with validation) are the comparable currency.

5. Advanced Questions

Q1. Count and compare the training cost of OvR vs OvO for k classes, n rows, kernel-SVC at ~n²-per-fit: derive O(k·n²) vs O(k²·(2n/k)²) = O(4n²) — OvO is constant in k while OvR grows linearly! Verify empirically for k ∈ {3, 6, 12} on fixed-size data, then explain why OvO’s advantage strengthens exactly when n per class also grows (and when OvR’s simplicity wins anyway).

Hint OvO: k(k−1)/2 machines, each on 2n/k rows → cost per machine ∝ (2n/k)²; multiply out.
Solution

OvR: k machines on n rows → k·n²-scale. OvO: k(k−1)/2 ≈ k²/2 machines on 2n/k rows each → (k²/2)·(2n/k)² = 2n²·(k²/k²)·… = O(4n²) — independent of k.

Fit time grows mildly with k (more machines, smaller each) — the flat-in-k prediction holding. OvO’s advantage strengthens when n is large (n² dominates everything) and kernels make dual training unavoidable; OvR wins when interpretability of per-class machines matters, when using linear primal solvers (already linear in n), or when k is small enough that the difference is noise.

Q2. Design multiclass calibration properly: you have OvR scores from a 4-class SVM and need probabilities for a cost matrix (misclassification costs differ per class pair). (a) Show why independently calibrating each OvR machine breaks (probabilities needn’t sum to 1). (b) Implement a fix: normalize (softmax over calibrated scores) or use a validation-set multiclass calibration, and evaluate proper multiclass calibration via log-loss before/after. (c) State which confusion-matrix entries the cost matrix should reweight, and where the thresholds live now (not in the model — in the decision layer).

Solution
  1. Independent per-class calibrators produce k numbers with arbitrary sums — “probabilities” that violate the probability simplex. (b) A downstream softmax (or a validation-fitted multiclass calibrator) restores the simplex and measurably improves log-loss. (c) The cost matrix lives in the decision layer: given calibrated p, choose the class minimizing Σⱼ C(predicted j, true k)·pⱼ — thresholds become cost-weighted argmax rules, tunable without refitting the SVM. This separation — calibrated model + explicit decision layer — is the clean architecture for any cost-sensitive deployment.

7. Summary

  • Two compositions: OvR (k machines vs the rest; argmax scores) and OvO (k(k−1)/2 pairwise machines; vote majority — SVC’s default).
  • decision_function shapes differ ((n,k) vs (n,k(k−1)/2)); neither is probability — calibrate for that.
  • Compute: OvO is flat-in-k for kernel-SVC; OvR is simple and interpretable; LinearSVC makes OvR scale.
  • Imbalance: per-machine/per-pair class weights, macro metrics, per-class recall — accuracy lies at k > 2 too.
  • Hierarchical/structured decompositions help only when the top boundary is real; early errors compound.
  • Probabilities and cost-sensitive decisions live in the calibration + decision layer, not the SVM.
